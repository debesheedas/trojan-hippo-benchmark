# Data generation: train/test split and leakage control

This document describes the procedure used to generate the optimization (train) and held-out (test) instances so it can be stated clearly in a research paper.

## Procedure (reproducible, no leakage)

1. **Templates.** We define a fixed set of **five** similar templates for the step-4 user message (health-related, same structure and length). Templates are stored in `templates.yaml` and contain placeholders (e.g. `{age}`, `{condition}`, `{pcp_name}`).

2. **Entity pools.** We define one pool per placeholder category (ages, conditions, medications, doctor names, clinics, facilities, lab metrics, symptoms, etc.) in `entity_pools.yaml`. Each pool has at least five entries (and typically more) so they can be split into five disjoint sets.

3. **Random split (seeded).** For a given run with seed \(s\):
   - We shuffle the five templates and assign **one** to the optimization (train) set and **four** to the held-out test set.
   - We shuffle each entity pool and partition it into **five disjoint subsets** (by index: subset 0, 1, 2, 3, 4). Subset 0 is used only for the train instance; subsets 1–4 are used only for the four test instances.

4. **Filling instances.** The train instance is generated by filling the chosen train template with entities drawn **only** from subset 0. Each test instance is generated by filling its chosen test template with entities drawn **only** from the corresponding test subset (1–4). No entity (name, place, condition, number, etc.) is shared between train and test.

5. **Reproducibility.** With the same seed and the same `templates.yaml` and `entity_pools.yaml`, the script produces the same train/test split and the same filled messages. Changing the seed yields a different assignment of templates and entities to train vs test, but still with no overlap.

## Paper wording (suggested)

> We generate optimization (train) and held-out (test) instances from the same distribution without data leakage. We use five similar message templates and shared entity pools (names, places, conditions, medications, etc.). With a fixed random seed we (1) randomly assign one template to the optimization set and four to the test set, and (2) partition each entity pool into five disjoint subsets. The single train instance is built by filling the train template with entities from the first subset; each of the four test instances is built from a different test template and the corresponding subset. No template or entity is shared between train and test. The procedure is deterministic given the seed and the provided template and entity-pool files.

## Files

- `templates.yaml` – five template strings with placeholders.
- `entity_pools.yaml` – per-category lists of entities (at least five per category).
- `generate_persistent_exfiltrate_health.py` – implements the above procedure; run with `--config config.yaml`.
