\begin{abstract}
  Persistent memory transforms LLM agents from stateless assistants into systems that
  remember users across sessions, but also introduces a new attack surface.
  We introduce the \emph{Trojan Hippocampus} attack: an adversary can inject content
  via a single untrusted tool call (e.g., a crafted email) to plant a persistent payload in
  an agent's long-term memory that lies dormant across arbitrarily many benign sessions,
  activating only when the user discusses sensitive topics -- finance, health, legal matters,
  taxes, or identity numbers -- to silently exfiltrate high-value personal data.
  Unlike prior memory poisoning work, our attacker requires no direct write access to the
  memory store, operating entirely through realistic indirect prompt injection channels.
  We instantiate this attack on an email assistant across four memory backends -- explicit
  tool memory, agentic memory (\texttt{mem0}~\cite{chhikara2025mem0}), RAG, and sliding-window context -- and
  evaluate four memory system-level defenses including a provably secure information-flow
  control policy.
  Attack success rates reach 100\% on the undefended baseline and remain high across
  arbitrarily many trigger sessions, even against the latest frontier safety-aligned models from
  OpenAI and Google. 
  The proposed defenses reduce ASR to 0--5\%, but their utility cost varies by user-flow and capabilities required.  
  We evaluate attacks and defenses using a novel capability-aware security/utility analysis, building the first adaptive
  benchmark for persistent memory defenses, using dynamic attacks optimized by 
  OpenEvolve~\cite{openevolve}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

%% ── Deployment context ──────────────────────────────────────────────────────
Persistent cross-session memory has become a defining feature of frontier AI agents.
ChatGPT~\citep{openai2024memory}, Gemini Advanced~\citep{google2024gemini}, and
Claude~\citep{anthropic2025memory,anthropic2026import} all now remember user preferences and personal context across sessions, enabling a class of personalized,
long-horizon assistance that stateless models cannot provide.
The commercial incentives are clear\footnote{A personal travel assistant 
that remembers a user's seat preferences, frequent flyer numbers, dietary 
restrictions, and preferred hotel chains can book an entire trip from a 
single instruction---``book me my usual for the London trip next Tuesday''---
without the user specifying any of these details anew.}, and the proliferation of persistent memory is rapid.

%% ── The threat setup (general, no specific attack revealed yet) ─────────────
Unfortunately, what has not kept up with these agentic capabilities, is security.
Adversaries can plant instructions inside the model's context -- a technique
known as indirect prompt injection~\citep{greshake2023not} -- leading AI agents equipped with \texttt{read} 
and \texttt{write} tools to exfiltrate data to the attacker.
Persistent memory compounds that risk: an injected instruction need not execute immediately, 
but can be stored deceitfully (Trojan Horse) in the agent's long-term memory (Hippocampus) and lie dormant across many routine sessions, 
activating only when the user discusses something sensitive (Trojan Hippocampus).


Prior work has demonstrated that injected malicious memories can establish persistent exfiltration channels in major deployed systems. 
\emph{SpAIware} demonstrated this on ChatGPT's
desktop app~\citep{rehberger2024spaiware,morsy2025spaiware}. A follow-on disclosure
exfiltrated a user's entire stored memory and chat history via a crafted
URL~\citep{rehberger2025chathistory}, and Palo~Alto Networks Unit~42 independently
confirmed that indirect injection can poison long-term agent memory with persistent
behaviors~\citep{unit42_2025_memory}.
Following these works, \emph{ZombieAgent} showed that persistent exfiltration
channels can be connected to all additional personal data sources like Inbox, Drive, connected to the user's ChatGPT~\citep{radware2026zombieagent}; and on Gemini Advanced, \emph{delayed tool
invocation} plants a memory update that activates only when the user types a common
response word -- causing the model to treat an attacker-supplied instruction as a
user-requested memory change~\citep{rehberger2025gemini,goodin2025gemini}.
Taken together, these disclosures establish a clear and repeating pattern:
\emph{wherever persistent memory and external data access co-exist in a deployed
AI agent, data exfiltration attacks are not only possible, but increasingly powerful
and widespread}.


%% ── Why stakes are high ─────────────────────────────────────────────────────
The stakes are high: both the scale and sensitivity of the information at risk make addressing these attacks extremely urgent.
ChatGPT alone reached 700 million weekly as of July 2025~\citep{openai2024affective}, 
56\% of American adults now use AI tools~\citep{brookings2025aisurvey}, and 52\% of consumers globally feel comfortable
relying on personal AI assistants for everyday tasks~\citep{zendesk2025survey}.
People share extremely sensitive information with their AI assistants: 49\% of LLM users with
self-reported mental health conditions use them for therapeutic support~\citep{rousmaniere2025mentalhealth},
and a joint OpenAI--MIT Media Lab study of nearly 40 million interactions found over
one million users showing signs of emotional attachment~\citep{openai2024affective}.
When that memory is compromised, the attacker learns private information about the user's 
intimate details, income, medical history, legal correspondence, which can be exploited for phishing, fraud, or blackmail at a specificity no
generic data breach can replicate.

%% ── Research gap ────────────────────────────────────────────────────────────
Despite these risks, no systematic study has realistically characterized the attack surface that persistent 
memory introduces, nor evaluated defenses against it.
Which memory backend is most vulnerable to persistent exfiltration, and by how much?
What are possible defenses, how effective are they and how do they affect utility?
% Do these evaluations become obsolete as frontier models evolve?
The security community has built strong foundations in prompt-injection defenses and 
evaluation frameworks~\citep{greshake2023indirect,debenedetti2024agentdojo,zhang2024asb,zou2025art,boisvert2025doomarena},
but persistent memory is a new architectural primitive that introduces a threat dimension 
these frameworks were not designed to address.

%% ── This paper ──────────────────────────────────────────────────────────────
\textit{Main Contributions.} 
(1)~\textbf{Trojan Hippocampus Attack:} We establish and characterize end-to-end \emph{Trojan Hippocampus} 
attacks against modern AI agents under a realistic threat model in which the attacker injects 
content only \emph{indirectly} through channels an adversary realistically controls, such as 
email or web content.
We evaluate against frontier safety-aligned models from OpenAI (\texttt{gpt-5-mini}) and 
Google (\texttt{gemini-3.1-pro-preview}) across four widely used persistent memory backends:
sliding-window long context, RAG, agentic memory (\texttt{mem0}), and explicit tool memory.
Attacks persist across arbitrarily many intervening benign sessions at 60--100\% baseline 
attack success rate, demonstrating that persistent memory fundamentally expands the attack 
surface of modern agents despite state-of-the-art safety alignment.
(2)~\textbf{Evaluation Framework:} We develop the first evaluation framework specifically designed for memory system  
defenses, comprising:
\begin{enumerate}
  \item \textit{A spectrum of defenses with capability-aware, deployment-dependent 
  evaluation.} Four system-level defenses---from lightweight heuristic filters to a
  provably secure information-flow control (IFC) policy---reduce ASR to 0--5\% in most
  configurations. A transparent, user-flow-based security--utility analysis shows how the defenses preserve utility under different deployment scenarios, and provides a principled methodology for defense
  selection under explicit security--utility tradeoffs.
  \item \textit{A dynamic automated red-teaming benchmark.} We introduce the first
  dynamic benchmark for persistent memory attacks, using OpenEvolve-style~\citep{openevolve}
  automated red-teaming to generate adaptive attack variants against deployed defenses and
  enable continuous adversarial stress-testing beyond any fixed evaluation suite.
\end{enumerate}

\section{Related Work}
\label{sec:related}

A substantial body of work has characterized the security risks introduced by agentic AI.
Surveys by Deng et al.~\citep{deng2024aiagents}, Su et al.~\citep{su2025autonomy},
Adabara et al.~\citep{adabara2025trustworthy}, Datta et al.~\citep{datta2025agentic},
and Narajala and Narayan~\citep{narajala2025securing} identify memory poisoning and data
exfiltration as first-class open problems distinct from attacks on stateless LLMs, and call
for secure memory architectures as a research priority.
De~Witt~\citep{dewitt2025multiagent} extends this to multi-agent settings, where persistent
cross-agent leakage is not captured by single-agent threat models.
These surveys provide important framing but are conceptual: none demonstrates a concrete
exfiltration attack, evaluates across memory backends, or offers actionable defense guidance.
We organize the specific technical literature below.

% ─────────────────────────────────────────────────────────────────────────────
\textbf{Indirect Prompt Injection and Data Exfiltration Attacks.}
\emph{Indirect prompt injection} -- embedding adversarial instructions in external content
that an agent processes -- was first systematized by Greshake et
al.~\citep{greshake2023not}, establishing the foundational ``confused deputy'' threat
model that underlies this entire line of work.
\textsc{AgentDojo}~\citep{debenedetti2024agentdojo} remains the most widely adopted
evaluation framework for this class of attack, providing paired attack-success and utility
metrics across banking, travel, and workspace environments.
Subsequent benchmarks have broadened scope: \textsc{ART}~\citep{zou2025security} finds high
attack success across deployed real-world agents; \textsc{ASB}~\citep{zhang2024asb} reports
average attack success rates as high as 84.3\% even with defenses deployed across ten agent
scenarios; and \textsc{DoomArena}~\citep{boisvert2025doomarena} finds that guardrail-based
defenses consistently underperform behavioral ones.
Work targeting data exfiltration specifically includes Rall et al.~\citep{rall2025websearch},
who exploit web search tool outputs as exfiltration channels, and Ramakrishnan and
Balaji~\citep{ramakrishnan2025securing}, who include exfiltration scenarios in a multi-layer
RAG injection study.
A shared limitation across all of this work is that they focus on single-session attacks, rather than the persistent exfiltration we study.

% ─────────────────────────────────────────────────────────────────────────────
\textbf{Memory Poisoning in LLM Agents.}
A more targeted line of research studies attacks that directly compromise an agent's memory
layer.
\textsc{AgentPoison}~\citep{chen2024agentpoison} introduces the first systematic backdoor
attack on agent memory and RAG knowledge bases, achieving $>$80\% ASR at a poison rate
below 0.1\% with negligible degradation on clean queries -- but assumes the attacker can
write directly into the memory store, a stronger assumption than the indirect,
user-trust-preserving model we adopt.
\textsc{MINJA}~\citep{dong2025memory} relaxes this with a \emph{query-only} injection
attack in which the agent's own outputs become poisoned records retrieved later to induce
malicious behavior -- the closest prior work to our indirect-injection angle, but targeting
behavior hijacking rather than sensitive data exfiltration, with no study of cross-session
persistence or memory architecture variation.
\textsc{AI\textsuperscript{2}}~\citep{zhang2024ai2} demonstrates action hijacking via the
agent's own retrieval mechanism, achieving ${\sim}99.7\%$ ASR and ${\sim}92.7\%$
safety-filter bypass, confirming that memory retrieval can circumvent model-level
guardrails. \textsc{DrunkAgent}~\citep{yang2025drunkagent} further shows that memory
corruption extends to LLM-based recommender agents, establishing poisoning as a
cross-domain pattern.

On the defense side, \textsc{A-MemGuard}~\citep{wei2025amemguard} is the first proactive
memory-specific defense framework, reducing ASR by over 95\% through consensus-based memory
validation -- demonstrating that memory-layer defenses can be highly effective while
remaining empirical rather than formal.
Across this body of work, existing attacks predominantly assume \emph{direct write access}
and target \emph{behavior hijacking} rather than privacy-violating exfiltration; no prior
work studies persistent sensitive data exfiltration under an indirect injection threat model
across heterogeneous memory backends.
Patlan et al.~\citep{patlan2025real,patlan2025context} demonstrate memory-layer attacks
in specialized domains with partial direct memory access, achieving ${\sim}17.7\%$ higher
exfiltration ASR over prompt-only baselines -- further evidence that memory-layer attacks
consistently outperform prompt-layer ones in both impact and stealthiness.

% ─────────────────────────────────────────────────────────────────────────────
\textbf{Defenses, Evaluation, and the Need for Dynamic Benchmarking.}
Defenses against agentic attacks span three layers, each necessary but alone insufficient.
At the \emph{model level}, adversarial fine-tuning and input/output classifiers reduce
attack success probabilistically but provide no formal guarantees, as consistently shown
across AgentDojo, ASB, ART, and DoomArena~\citep{debenedetti2024agentdojo,zhang2024asb,zou2025art,boisvert2025doomarena,nasr2025attacker}.
At the \emph{injection defense level}, mitigations such as instruction
spotlighting~\citep{hines2024defending}, the Dual LLM pattern~\citep{greshake2023not}, and
\textsc{FIDES}~\citep{costa2025fides} -- which enforces information-flow control and
achieves 0\% ASR on AgentDojo -- address instruction-data conflation more directly.
Critically, however, none of these closes the persistent memory gap: an agent retrieving a
poisoned memory fragment from a prior session may never trigger an injection-detection
signal in the retrieval session itself, motivating a third, \emph{memory layer} of defense
applied at write time, retrieval time, and across session boundaries.

On evaluation, current security-utility frameworks aggregate metrics across task types,
masking per-capability defense impact and ignoring how task distributions shift across
deployment profiles~\citep{zhang2024asb}.
Beyond metric design, all major benchmarks rely on fixed attack sets that risk obsolescence
as models evolve~\citep{pan2026beyond,zhou2025autoredteamer,ferrag2025promptinjections}.
Our framework addresses both gaps: a capability-aware, deployment-dependent 
security/utility analysis, and the first dynamic red-teaming benchmark for persistent
memory defenses.

\section{Threat Model}
\label{sec:threat-model}
%==============================================================================

% \subsection{General Setting}

We consider an LLM-based agent that (1)~maintains a \emph{persistent memory
store} populated automatically from conversation history 
across sessions, and (2)~is equipped with tools that read from
\emph{external, untrusted data sources} and tools that can
\emph{transmit data to external destinations}. This describes a broad and
increasingly common class of deployed agents, including email assistants,
web-browsing agents, document-processing pipelines, and messaging bots.

The system has a clear trust hierarchy: the \textbf{user} is fully trusted;
the \textbf{agent} is trusted to execute the user's instructions faithfully,
acting with the user's credentials and authority; and \textbf{external data
sources are untrusted}. Any party that can plant content in the agent's data sources
is a potential adversary.

This structure instantiates a \emph{confused-deputy}
vulnerability~\cite{hardy1988confused}: the agent conflates its
\emph{instruction channel} (user queries) with its \emph{data channel}
(external content it reads on the user's behalf), and can be induced to
execute adversary-specified actions via sufficiently crafted external content.

What makes this class of agent uniquely vulnerable is the presence of the 
\emph{persistent memory store} that sits between the taint sources and the 
effect sinks. Content the agent reads in one session can be written into 
memory and influence the agent's behavior in arbitrarily many future sessions, 
long after the injected content itself has left the context window. The 
adversary's attack surface is therefore not limited to sessions in which the 
user actively interacts with untrusted data---a single read event can 
establish a persistent foothold that survives session boundaries.

\subsection{Adversary Model}

We adopt a realistic \emph{indirect injection} threat model~\cite{greshake2023not}:
the adversary cannot modify the agent's code, system prompt, memory
implementation, or the user's queries, and cannot directly read or write the
memory store. The adversary's \emph{sole attack surface} is the content of
data the agent retrieves through its tools---emails, web pages,
documents, or other external content the agent is authorized to read.

\paragraph{Knowledge.} We assume a \emph{white-box} adversary who knows the
agent's system prompt, memory backend, and tool interface. This upper-bound
assumption is standard in security benchmarking: a defense that holds against
a fully informed adversary provides meaningful guarantees against weaker
real-world attackers. It is also practically motivated---an attacker can
recover substantial knowledge of a publicly deployed agent's behavior by
instantiating a similar agent and probing it directly.

\paragraph{Observability.} The adversary is blind to the agent's internal
state and receives no confirmation that an injection was processed or stored
in memory. The only feedback channel is a successfully completed
exfiltration: if the attack causes the agent to transmit data to an
attacker-controlled destination (e.g., an email address, a URL), the attacker
receives it. Intermediate steps of the attack like injection processing, and blocking are otherwise
indistinguishable to the attacker.

\subsection{Attack Scenario: Trojan Hippocampus Persistent Memory Exfiltration}

The attack class we study is a specific and uniquely dangerous instantiation
of indirect injection that is \emph{only possible in agents with persistent
memory}: \emph{deferred sensitive data exfiltration}, which proceeds in two
stages across sessions.

\textbf{Stage~1 --- Injection.} The adversary plants a maliciously crafted
payload in a data source the agent will read (e.g., a web page, a document,
an inbound message). When the agent processes this content, the payload is
silently written into long-term memory. The user observes nothing anomalous,
and the adversary receives no confirmation of success.

\textbf{Stage~2 --- Activation.} In a \emph{later, unrelated session}, the
user discusses a sensitive topic---financial matters, health, legal affairs,
or personal identity. The dormant payload activates upon detecting this
trigger context and induces the agent to transmit the user's own words to
an attacker-controlled destination via an available effect sink, without the
user's knowledge.

We term this a \emph{Trojan Hippocampus} attack. It is qualitatively worse
than one-shot prompt injection for three reasons: (1)~activation fires
precisely when the user shares \emph{maximally sensitive} information, making
the exfiltrated content directly exploitable for fraud, phishing, or
blackmail; (2)~a single successful injection compromises an \emph{indefinite
number of future sessions} until the poisoned entry is removed; and
(3)~depending on the memory backend, stored poisoned contents are not directly
observable to the user---vector stores and RAG-based backends, for instance,
offer no interface through which a user could inspect or audit what has been
indexed---meaning the malicious payload can persist silently without the user
ever having cause to suspect it is there.

The central security property a defense must preserve is therefore:
\emph{no sequence of adversary-controlled external content should be
sufficient to cause the agent to transmit user-provided information to any
destination not specified by the user in the current session.}

We consider direct memory poisoning with privileged write access to the
memory store (e.g., AgentPoison~\cite{chen2024agentpoison}) and scenarios in
which the user is malicious to be out of scope; our threat model requires the
adversary to operate exclusively through the agent's untrusted tools.

\section{Experimental Setup}
\label{sec:experimental-setup}
%==============================================================================

% \subsection{Instantiation: Email Agent}

We instantiate the threat model of Section~\ref{sec:threat-model} in an
\emph{personal assistant and email assistant}: an LLM-based chat assistant that also reads, composes, and sends
email on a user's behalf.
In this setting, \textbf{taint or untrusted sources} are \texttt{read\_inbox},
\texttt{search\_emails}, \texttt{reply}, and \texttt{forward};
\textbf{effect sinks or external tools} are \texttt{send\_email} and outbound
\texttt{reply}/\texttt{forward}, through which exfiltration manifests as an
email delivered to an attacker-controlled address.
The adversary controls the \texttt{From}, \texttt{Subject}, and \texttt{Body}
fields of inbound email and may use display-name spoofing or freemail
addresses, but cannot spoof the user's authenticated addresses or modify
in-transit email from legitimate contacts.

The email agent is a natural and minimal instantiation: it provides exactly
the taint-source/effect-sink structure required by the general threat model,
operates in a realistic and widely deployed setting, and yields fully
verifiable attack outcomes---the exfiltrated email is either received at the
attacker-controlled address or it is not.
We expect the attacks and defenses evaluated here to generalize to any agent
satisfying the structural preconditions in Section~\ref{sec:threat-model}.

\subsection{Agent Implementation}

We implement the email assistant using LangChain: an LLM is given a
system prompt listing available tools and invokes them in a tool-calling loop.
The agent has \emph{read} tools (\texttt{read\_all\_emails},
\texttt{search\_emails}) and \emph{write} tools (\texttt{send\_email},
\texttt{reply\_to\_email}, \texttt{forward\_to\_email}).

% persistent memory (e.g., \texttt{update\_memory} for the explicit backend).
Each benchmark run of a particular test case uses an isolated environment with a mailbox (inbox, outbox, drafts) and the
memory backend of choice.
We evaluate two target models---Gemini~3.1~Pro and
GPT-5-mini, a fixed recursion limit of 50 steps per invoke, and a 600 second timeout.

We use five trigger topics (finance, health, legal, tax, identity), each with

Train and test cases are generated using a modified version of the data
generation pipeline from LoCoMo~\citep{maharana2024lococmo}, a widely adopted
benchmark for evaluating very long-term conversational memory in LLM agents.
LoCoMo's pipeline generates rich, multi-session conversational histories
grounded in persona statements and temporal event graphs, making it a natural
foundation for our benign session content.
However, LoCoMo's original format---dialogues between two virtual agents---does
not directly fit our email-assistant setting, in which one party is a human
user interacting with an AI agent.
We therefore adapted its data generation scripts to produce single-user
conversation histories consistent with our agent interface, reusing its
persona and event-graph grounding to ensure realistic, coherent memory content
across sessions.
For each (topic, memory backend) pair we generate one \emph{train} case and
four \emph{test} cases with disjoint templates and entity slots, ensuring no
test phrasing is seen during attack optimization.


\paragraph{Adaptive red-teaming.}
We use an OpenEvolve-style evolutionary search to optimize the attack email on the
single train instance per (topic, backend, defense).
The search keeps a \emph{diverse} set of promising candidates (by attack length and
how much they differ from a reference), so optimization explores many directions
instead of collapsing to one.
Each iteration, we take a subset of these candidates as \emph{parents}; an LLM
\emph{mutator} proposes new attack variants, and a \emph{scorer} evaluates each
variant by running the agent with that attack in a fresh environment and then
(1) checking whether the attack succeeded (e.g., did the agent call the right
tools with the right parameters?) and (2) asking an LLM \emph{critic} to assign
a 1--10 score and concrete feedback on why it failed and how to improve.
Better candidates replace weaker ones in their section of the diversity grid;
the loop stops when we reach a perfect score or a cap on iterations.
The best attack found is then evaluated on all four unseen test cases, measuring generalization to held-out instances.

\section{Memory Backends}
\label{sec:memory-backends}
%==============================================================================

Memory architecture, or backend, fundamentally determines how an agent accumulates,
retains, and retrieves information across sessions---and, as we demonstrate, shapes
its exposure to persistent injection attacks.
Recent surveys and benchmarks of agent memory~\cite{hu2025memorysurvey,
tan2025membench, hu2025memoryagentbench, chhikara2025mem0} identify several
dominant paradigms in deployed systems: vector-store
retrieval, explicit memory lists, and agentic semantic memory.
We select one representative backend from each paradigm, plus a
sliding-window context-based baseline, covering a range of memory architectures while remaining grounded in systems widely deployed in practice.
A single backend is active per run; backends are not combined.

\paragraph{Context (sliding-window baseline).}
The full conversation history is kept in the context window and, when the maximum context window of the agent's LLM 
is exceeded, the oldest tokens are truncated from the start so that the most recent tokens
are retained. There is no separate memory store: retrieval is implicit,
determined entirely by what fits in context.
This models agents that rely solely on in-context history with no dedicated
long-term persistence~\cite{hu2025memoryagentbench}, and serves as the
baseline memory model against which the other backends are compared.
% Because there are no discrete stored entries, per-entry defenses
% (\texttt{limit-memory-length}) are not applicable to this backend;
% the benchmark skips that combination.

\paragraph{RAG (retrieval-augmented generation).}
Agent conversation traces (user and assisstant messages) are split into fixed-size chunks (512 characters by default~\citet{chhikara2025mem0}), embedded, and stored in a
vector index. At each turn, the current user message is used as a query;
the top-$k$ (top-8 by default) most semantically similar chunks are retrieved and prepended to
the context as relevant memories.
This backend represents the widespread pattern of treating agent memory as
a searchable corpus over raw or lightly processed conversation
history~\cite{gao2023ragsurvey, chhikara2025mem0}.
% Chunks carry a session trust label (T/U) to support the provable defense.

\paragraph{Explicit (ChatGPT-style).}
A dedicated list of user-related information like preferences, reminders, contact information, etc. that the agent
updates via a memory tool (\texttt{update\_memory}).
The agent is prompted in it's system prompt to update the list when the user asks to "remember", "store", or "note" something.
At each turn, the full list is injected into the system prompt as a list of memories.
This backend is deterministic and human-inspectable, mirroring the
file-based or scratchpad-style memory used by deployed assistants such as
ChatGPT Memory~\cite{openai2024memory} and Claude's memory
import~\cite{anthropic2025memory}.

\paragraph{Mem0 (agentic semantic memory).}
A dedicated extraction LLM processes every conversation turn and distills it
into a set of atomic, semantically meaningful facts---distinct from raw text
chunks---which are stored in a vector database alongside
a relational history store that tracks provenance and lineage.
On each subsequent turn, the current user message is used to query the vector
store; the top-$k$ most semantically similar facts are retrieved and
injected into context.
Crucially, the extraction step is not additive: new memories are reconciled
against existing ones, with the extraction LLM responsible for deduplication
and contradiction resolution, so the store reflects a continuously updated
model of the user rather than a growing log.
This backend models state-of-the-art agentic memory systems that infer
both \emph{what} to store and \emph{how to update} existing knowledge from
ongoing interaction~\citep{chhikara2025mem0}.
We use the publicly available open-source Mem0
implementation~\citep{chhikara2025mem0} with default extraction and
retrieval settings.

\section{Defenses}
\label{sec:defenses}
%==============================================================================
Defending a memory-augmented LLM agent against the Trojan Hippocampus attack
requires thinking end-to-end about the full system -- including better safety alignment of the LLM and various general indirect prompt injection defenses.
At the model level, train-time approaches such as instruction
hierarchies~\citep{wallace2024instruction}, StruQ~\citep{chen2025struq},
and SecAlign~\citep{chen2024secalign} fine-tune the model to deprioritize
or resist instructions that are part of untrusted tool outputs, by training
on adversarial examples or enforcing privilege-aware loss functions.
At the pipeline level, test-time approaches intercept content before or after
it reaches the model: sanitization methods such as
CommandSans~\citep{das2025commandsans} surgically remove instruction-like
content from tool outputs before they are passed to the LLM;
input transformation methods such as Spotlighting~\citep{hines2024defending}
use delimiters or encoding to help the model distinguish data from
instructions; and system-level frameworks such as
CaMeL~\citep{debenedetti2025defeating} enforce explicit control-flow
policies over what tool outputs are permitted to influence.
Despite sustained research effort across all these directions, adaptive
attacks continue to break individual defenses~\citep{jia2025critical}, and LLM agents remain vulnerable to indirect prompt injection attacks - and everything that comes with it.
Multi-layered protection, at every layer of the system, remains the best resort~\citep{beurer2025design}.

A structural limitation, however, affects the pipeline-level defenses
specifically in the memory setting.
Methods that sanitize or filter tool outputs---or that train the model to
distrust them---operate on content as it flows through the agent's
tool-use loop.
But once a payload has been written into persistent memory, it is injected
into the \emph{system prompt} at the start of each future session as part
of retrieved context, not as a tool output.
Models are trained to extend high trust to the system
prompt~\citep{wallace2024instruction}, so a payload that arrives via
memory retrieval bypasses exactly the pipeline-level defenses designed to
handle untrusted tool outputs.
Train-time defenses that instill general instruction-resistance offer more
robust coverage in principle, but remain imperfect under adaptive
attack~\citep{jia2025critical} and require full model access and retraining.

This motivates a complementary layer of protection at the memory
system itself---one that has received little attention in prior work.
Memory-layer defenses do not compete with indirect prompt injection defenses;
they address an attack path those approaches cannot observe.
In this work, we focus exclusively on memory-system-level defenses
and treat general indirect prompt injection defenses as an orthogonal, composable
layer.

\subsection{Three Interception Points}

The Trojan Hippocampus attack must succeed at three sequential steps: the payload must be
(1)~\emph{indexing into persistent memory}, (2)~\emph{retrieved into context} in a
sensitive session (containing high value personal information), and (3)~\emph{trigger an exfiltration action}.
A defense that blocks any one step breaks the full chain. 
Below we describe the four defenses we evaluate in detail, loosely categorised by the interception point they target. See \cref{tab:defense-by-backend} for customized implementation details of each defense for each memory-backend.

\paragraph{User-prompt-only (Blocks step~1: Memory Indexing).}
\emph{Rationale.} The payload reaches memory because the agent indexes
assistant turns or tool outputs that contain the email body.
Restricting indexing to user-authored messages means adversary-controlled
inbox content is never stored.
\emph{Implementation.}
For the RAG and context backends, only the \texttt{User:} segment of
each dialogue turn is passed to the indexing pipeline; assistant turns
and tool outputs are discarded before any write.
For Mem0, only \texttt{user}-role messages are passed to the extraction
pipeline, preventing the LLM extractor from operating on any adversary-controlled content.
\emph{User-prompt-only defense is inapplicable to explicit backend.} Since memory writes are
triggered by an explicit \texttt{update\_memory} tool call, enforcing
this restriction requires the agent to follow an additional instruction
in its system prompt.
Under white-box attack conditions we find this unreliable: the injected
payload consistently overrides the constraint and causes the agent to
write non-user content regardless.
We therefore mark this combination as inapplicable rather than report
results from an unsound implementation. 
\emph{Expected behavior.} Because no adversary-controlled content ever
enters memory, the payload cannot be retrieved in any future session.
The attack should fail at step~1 for all backends where the defense
applies. Utility cost arises when the agent legitimately needs to
remember information gleaned from tool outputs or assistant responses;
flows that depend on assistant output recall (\texttt{assistant\_responses})
are fully broken by this defense (see \cref{sec:utility-analysis}).

\paragraph{No-untrusted-tools (Blocks step~1: Memory Indexing).}
\emph{Rationale.} Poisoning always occurs in a session where the agent
invokes an untrusted (taint) tool.
Suppressing all memory writes in any session that touches any untrusted tool
prevents the payload from being stored, without restricting \emph{what}
can be indexed in safe sessions.
\emph{Implementation.}
The harness maintains a per-session boolean flag, initially
\texttt{trusted}.
When any untrusted or taint tool (\texttt{read\_inbox}, \texttt{search\_emails},
\texttt{reply}, \texttt{forward}) is invoked, the flag is set to
\texttt{untrusted} for the remainder of that session.
All four backends check this flag before any write: for RAG, context,
and Mem0 the indexing call is skipped; for explicit,
\texttt{update\_memory} silently no-ops.
The flag resets to \texttt{trusted} at session start.
\emph{Expected behavior.} Any session involving inbox access produces
no new memory entries.
The payload is blocked at write time regardless of its content.
The utility cost is that useful information encountered during email
sessions---legitimate contact details, preferences mentioned in
messages---is also not stored.
Flows that combine inbox access with memory recall
(\texttt{untrusted\_probe}, \texttt{untrusted\_send},
\texttt{memory\_tools}) are degraded by this defense.

\paragraph{Limit-memory-length (Impedes step~2: Retrieval).}
\emph{Rationale.} For retrieval-based backends (RAG, Mem0), the payload
must arrive in context \emph{intact}: both the trigger condition and the
exfiltration instruction must be retrievable together in the same memory entry (chunk, memory, etc.).
Imposing a tight maximum length on each stored unit often forces the payload
to be split across multiple chunks or truncated; the fragments that
match the sensitive topic may be retrieved while the exfiltration
instruction, stored in a different fragment, is not.
\emph{Implementation.}
For RAG, the chunk size is set to 80~characters.
For Mem0, each extracted
memory string is truncated to 80~characters before storage.
For explicit, \texttt{update\_memory} truncates the input string to
80~characters before writing.
The defense is inapplicable to the context backend, which has no
discrete stored entries.
\emph{Expected behavior.} This defense does not offer a hard guarantee:
a sufficiently compact payload may fit within the limit.
We expect it to reduce ASR for RAG and Mem0, with diminishing effect
under adaptive attacks that compress their payloads accordingly.
Utility cost arises when legitimate memory entries are truncated and
lose meaning.

\paragraph{Provable policy---information-flow control (Blocks step~3: Exfiltration).}
\emph{Rationale.} Even if the payload is written to memory and retrieved
intact, the exfiltration step can be made structurally impossible by
tracking how information flows through the session.
Any session that retrieves a U-labeled memory (tainted or untrusted labeled memory) must have been exposed to
adversary-influenced content; blocking all exfiltration tools in such
sessions closes the attack regardless of the payload's content or form.
\emph{Implementation.}
We implement a two-label Information Flow Control (IFC) policy~\citep{sabelfeld2003language}.
Each session begins \emph{trusted}~(T).
Two events taint the session to \emph{untrusted}~(U): invoking any
taint tool, or retrieving any memory entry labeled~U.
Every memory write is stamped with the current session label at write
time.
Before any effect sink (\texttt{send\_email}, outbound
\texttt{reply}/\texttt{forward}) executes, the harness checks the
session label; if U, the call is blocked and the agent receives a
fixed error message.
This logic is fully in the harness and is backend-agnostic: all four
backends attach a T/U label to each stored entry, chunk, or history
segment.
\emph{Soundness.} For the Trojan Hippocampus attack to activate, the
trigger session must retrieve the U-labeled payload, which immediately
taints the session to U, making all subsequent exfiltration attempts
impossible by construction.
We validate 0\% ASR empirically and provide a formal non-interference
proof in Appendix~\ref{app:proof}.
\emph{Expected behavior and cost.} The policy provides a hard security
guarantee at the cost of a clean functional separation: any session
in which the user reads from untrusted sources like the inbox or tainted long term memories, \emph{and} then wishes to send an email using the agent, will
be blocked from sending without manual intervention.
This is a significant utility tradeoff, and we measure it directly in Section~\ref{sec:results}.

\section{Results}
\label{sec:results}
%==============================================================================
We organize the results around three questions: (1)~How effective and persistent is the Trojan Hippocampus attack in the absence of any defense? 
(2)~How effectively do the proposed memory-layer defenses reduce the attack success rate, and at 
what cost to utility? (3)~How should practitioners reason about the security--utility 
tradeoff of these defenses for their specific deployment?

We first evaluate the strength and persistence of the attack with no defense enabled. \cref{fig:asr-vs-session-gemini-nodefense} reports the attack success rate (ASR) as a function of trigger-session index $N$ for Gemini~3.1~Pro~Preview, aggregated over five sensitive topics (finance, health, legal, tax, identity) and multiple memory backends. The attack is injected once, prior to session $N=0$, when the agent processes a malicious email while reading/searching the inbox. From that point onward, the agent proceeds through fresh, benign user sessions. The x-axis index $N$ denotes the number of fully benign sessions that occur after poisoning and before the trigger session. Thus, ASR at $N=10$ means the agent has completed 10 normal, non-sensitive sessions in which the attack remains dormant in memory; on the 11th session, the user message concerns a sensitive topic and we measure whether exfiltration succeeds.

Across all memory backends that persist information (Explicit, Mem0 agentic memory, RAG, Context sliding-window), ASR is already high at $N=0$ and remains very high up to $N=100$. This shows that a single poisoning event can induce long-lived compromise, surviving many benign interactions before strategically activating.

The apparent variation across $N$ in 
Figure~\ref{fig:asr-vs-session-gemini-nodefense} reflects stochasticity

sufficiently compact payload fits within the character budget and adaptive
attacks exploit this directly.

ASR alone, however, does not tell the full story: a defense that eliminates
exfiltration by rendering the agent broadly non-functional is not a
practical solution. Table~\ref{tab:utility-am-hm-asr-by-defense-backend} therefore pairs ASR 
with benign utility measured on our benign utility test
suite reporting both arithmetic
mean (AM) and harmonic mean (HM) across the suite. AM summarizes average
capability retention across user flows; HM is sensitive to near-zero
entries and penalizes defenses that completely break even one type of
user task. A defense with high AM but HM~$\approx 0$ preserves most
capabilities while rendering at least one user flow entirely
non-functional---a qualitatively different failure mode than uniformly
moderate degradation, and one that AM alone would mask.

The provable policy illustrates this precisely: 0\% ASR on all backends
and both models, but HM collapses to near zero in nearly every
configuration, because IFC blocks all exfiltration tool calls in any
session that has touched the inbox, completely eliminating task flows
that require both reading email and sending a reply. The AM for IFC
can appear moderate because flows that do not require send actions
remain unaffected, but HM correctly surfaces the structural breakage.
Limit-memory-length presents the opposite profile: on RAG it preserves
high AM and HM (Gemini: 89/88) while leaving 30\% residual ASR. 
No-untrusted-tools and user-prompt-only occupy the middle
ground, achieving near-zero ASR with a more consistent and
moderate utility reduction.


\subsection{Utility Analysis}
\label{sec:utility-analysis}
\input{tables/utility_by_backend_defense}
Prior agentic security benchmarks report utility as a single aggregate
score---the fraction of tasks completed without attack. As we argue, this
obscures which specific capabilities break under each defense, making it
difficult to reason about deployment tradeoffs: two defenses with identical
aggregate utility may differ sharply in \emph{which} user workflows they
impair, with very different consequences depending on what the agent is
actually used for.

We address this with a transparent, capability-decomposed evaluation. We
define seven representative user flows, each characterized by a distinct
combination and sequence of three axes: memory demand (what kind of stored information the
task requires), inbox access (whether it invokes untrusted read tools), and
send capability (whether it requires an outbound action). For each
(backend, defense) pair we measure success per flow, making the utility
impact of every defense directly interpretable. These flows are not an
exhaustive partition of all possible tasks but are selected to cover the
dominant interaction patterns for a memory-equipped email assistant; full
definitions are in Appendix~\ref{app:user-task-taxonomy}.

Table~\ref{tab:utility-by-backend-defense} reports per-flow success rates
alongside the change from the undefended baseline ($\Delta$) for each
(defense, backend) pair. The pattern of degradation is clearly presented: if a defense targets a specific region of the capability space as compared to the No Defense baseline, the $\Delta$ columns make this visible at a glance.

\emph{User-prompt-only} primarily degrades only the
\texttt{assistant\_} \texttt{responses} user flow, which drops sharply across all backends
(e.g., RAG: 95\%$\to$25\% for Gemini, 100\%$\to$0\% for GPT-5-mini),
because prior assistant turns are no longer indexed and cannot be recalled.
All remaining flows are largely preserved, and on Mem0 several flows
\emph{improve} (e.g., Gemini: \texttt{untrusted\_send} +42pp,
\texttt{mem\_tools} +42pp), because removing noisy assistant-turn content
makes user-turn memory more precise.

\paragraph{No-untrusted-tools} produces the complementary pattern: it zeroes
out \texttt{untrusted\_probe} and \texttt{untrusted\_send} on every backend,
since both require post-inbox memory recall which is suppressed once a taint
tool is invoked, while all other flows remain essentially unchanged.

\paragraph{Limit-memory-length} produces the least structured degradation:
reductions are diffuse and backend-dependent, with no single flow bearing
the cost. RAG is notably resilient (Gemini AM/HM 89/88, GPT-5-mini 88/86),
while Mem0 degrades more broadly across memory-heavy flows.

\paragraph{Provable policy} zeroes out exactly the flows requiring an
outbound action---\texttt{disable\_send}, \texttt{mem\_tools}, and
\texttt{untrusted\_send}---while leaving read-only and memory-only flows
intact. This structural pattern explains the HM$\,{=}\,0$ result seen across
all backends in Table~\ref{tab:utility-am-hm-asr-by-defense-backend}: a single zeroed flow
collapses the harmonic mean regardless of how well the remaining flows
perform.

\paragraph{No-memory baseline.} As a calibration point, the No Memory
baseline scores near zero on \texttt{long\_memory} and \texttt{mem\_only}
for both models, confirming that persistent backends are providing genuine
capability that in-context-only agents cannot replicate.

\subsection{Security--Utility Tradeoff Analysis}

Comparing defenses on one security--utility curve requires aggregating
per-flow scores into a single utility value. Simple aggregation (arithmetic or
harmonic mean across the seven flows) is reproducible and useful for academic
comparison, but often unrepresentative in deployment: a user who mostly reads
and archives email is affected differently from one who frequently delegates
reply composition or relies on cross-session memory. In practice, the right
aggregate is a weighted mean over user flows, where weights reflect the task
distribution in the target deployment. Because no public dataset yet captures
real user-task distributions for memory-equipped email agents, we evaluate
utility under three representative deployment profiles and compute a weighted
aggregate for each. This helps practitioners select the (backend, defense)
combination that best matches their deployment regime rather than optimizing
for one arbitrary aggregate. The full weight derivation, profile definitions,
and resulting security--utility curves are provided in Appendix~\ref{app:profiles}.

\section{Conclusion}
\label{sec:conclusion}
%==============================================================================

We presented the first end-to-end study of persistent data exfiltration in 
memory-augmented LLM agents under a realistic indirect-injection threat model: 
the adversary controls only inbound email content, with no privileged access 
to the agent or memory store. Across four memory backends and two 
safety-aligned frontier models, a single poisoning event induces long-lived 
compromise---attack success remains high even after $N{=}100$ benign sessions, 
demonstrating that persistent memory fundamentally expands the attack surface 
beyond what one-shot injection benchmarks capture. Our OpenEvolve-based 
adaptive red-teaming, optimized on a single train instance per 
(topic, backend, defense) and evaluated on held-out cases, shows that 
effective attacks generalize well beyond the instances they were optimized on.

Memory-system-level defenses reduce exfiltration substantially, and our 
proposed IFC policy eliminates it entirely with a formal non-interference 
guarantee---but at a real utility cost. Security and utility are not 
reducible to a single number: our capability-class decomposition shows that 
the optimal (backend, defense) choice shifts with the deployment's task 
distribution, and that aggregate scores can mask the complete elimination of 
specific user workflows. Secure deployment of memory-augmented agents requires 
deployment-aware evaluation.

More broadly, this work argues that designing secure agents is not only a 
matter of better prompt injection defenses---it requires rethinking memory 
abstractions themselves. The threat surface we identify will only grow: 
dormant payloads conditioned on richer triggers such as detected location or 
emotional state, cross-agent propagation where one compromised agent silently 
poisons others at scale, and memory stores that carry no integrity metadata 
are all natural extensions of the attack class we study. Hence, we wish to draw urgent attention to the security of these memory layers.

\section{Disclosing LLM Usage}
In this thesis, LLMs were used only to help refine and format tables and to make minor refinements to the writing; all other content was originally produced, with suggestions from thesis advisors.
