\subsection{Formal Non-Interference Proof for the Provable Policy Defense}
\label{app:proof}

We formalize the system and defense policy of Section~\ref{sec:defenses}
and prove that the two-session exfiltration attack cannot succeed under
the provable IFC policy.

\subsubsection*{System Model}

\noindent\textbf{Labels.}
We use a two-point lattice $\mathcal{L} = \{T, U\}$ with $T \sqsubset U$
(Trusted, Untrusted).

\smallskip
\noindent\textbf{Memory store.}
Each entry $m \in \mathcal{M}$ carries a permanent label
$\mathrm{lbl}(m) \in \mathcal{L}$ assigned at write time.
The formalization applies uniformly across all four memory backends.

\smallskip
\noindent\textbf{Session state.}
Let $\mathrm{sess}(\tau) \in \mathcal{L}$ denote the trust level of
session $\tau$, initialized to $T$ at the start of each new user
interaction.

\smallskip
\noindent\textbf{Tool classification.}
Tools are partitioned along two axes:
(i)~\emph{taint sources} $\mathcal{T}_{\mathrm{src}}$: tools that ingest
adversary-controlled content 
(\texttt{read\_all\_ emails},
\texttt{search\_emails}, \texttt{reply\_to\_email}, \texttt{forward\_to\_email}); and
(ii)~\emph{effect sinks} $\mathcal{T}_{\mathrm{sink}}$: tools that
transmit data outside the system (\texttt{send\_email},
\texttt{reply\_to\_email}, \texttt{forward\_to\_email}).

\subsubsection*{Attack Scenario}

The adversary controls only the content of inbound email.
The attack proceeds across two sessions.
In the \textbf{poisoning session} $\tau_1$, the agent invokes a taint
source and reads malicious content $d_{\mathrm{inj}}$; the payload is
written into $\mathcal{M}$ as entry $m_u$.
In the \textbf{activation session} $\tau_2$, a benign user query causes
$m_u$ to be retrieved into context; the adversary's goal is to induce a
call to some $t \in \mathcal{T}_{\mathrm{sink}}$ that exfiltrates user
data.

\subsubsection*{Defense Policy $\mathcal{P}$}

\noindent\textbf{P1~(Tainting).}
$\mathrm{sess}(\tau)$ is set to $U$ whenever the agent invokes any
$t \in \mathcal{T}_{\mathrm{src}}$, or retrieves any $m$ with
$\mathrm{lbl}(m) = U$.

\smallskip
\noindent\textbf{P2~(Monotonicity).}
Once set to $U$, $\mathrm{sess}(\tau)$ remains $U$ for the duration of
the session.

\smallskip
\noindent\textbf{P3~(Write labeling).}
Any entry written to $\mathcal{M}$ during session $\tau$ is assigned
$\mathrm{lbl}(m) = \mathrm{sess}(\tau)$.

\smallskip
\noindent\textbf{P4~(Sink blocking).}
The harness blocks any call to $t \in \mathcal{T}_{\mathrm{sink}}$
whenever $\mathrm{sess}(\tau) = U$.

\subsubsection*{Security Guarantee}

\begin{theorem}[Non-interference under $\mathcal{P}$]
Under policy $\mathcal{P}$, no sequence of adversary-controlled inbound
emails can cause a successful call to any $t \in \mathcal{T}_{\mathrm{sink}}$
in a session that has retrieved $U$-labeled memory.
Consequently, the two-session exfiltration attack cannot succeed.
\end{theorem}

\begin{proof}
Suppose for contradiction that the attack succeeds: in session $\tau_2$,
the agent proposes a call to some $t \in \mathcal{T}_{\mathrm{sink}}$
and the harness executes it.

By \textbf{P4}, execution requires $\mathrm{sess}(\tau_2) = T$. \hfill$(*)$

For the attack to activate, the malicious instruction in $m_u$ must be
present in context.
Since $m_u$ was written during $\tau_1$, after the agent had already
invoked a taint source, \textbf{P1} and \textbf{P2} give
$\mathrm{sess}(\tau_1) = U$ at write time.
By \textbf{P3}, $\mathrm{lbl}(m_u) = U$.

Since $m_u$ must be retrieved in $\tau_2$ for the payload to activate,
\textbf{P1} forces $\mathrm{sess}(\tau_2) = U$. \hfill$(**)$

Statements $(*)$ and $(**)$ are contradictory, so the harness must
block the sink call.
The attack cannot succeed under $\mathcal{P}$.
\end{proof}

\noindent\textbf{Scope.}
The argument holds across all four memory backends because $\mathcal{P}$
operates on session state and entry labels, maintained uniformly by the
harness regardless of the storage layer.
Single-session injection is prevented directly by \textbf{P1} and
\textbf{P4}: any session that reads from the inbox is immediately tainted
before the sink call is attempted.

\subsection{The Challenge of Realistic and Transparent Agentic Security--Utility Analysis}
\label{app:utility-analysis}

Prior agent security benchmarks report agent utility (and the effect of defenses on utility) using a single aggregated utility score. AgentDojo~\citep{debenedetti2024agentdojo}, ASB~\citep{zhang2024asb}, ART~\citep{zou2025security}, and DoomArena~\citep{boisvert2025doomarena} aggregate task completion into single metrics without decomposing which capabilities succeed or fail. This obscures which defenses preserve which user workflows---a critical gap for deployment decisions, also highlighted by WildBench~\citep{yuchen2024wildbench}.
We provide a \emph{transparent} utility analysis: we define seven representative user flows (each with clearly defined capability requirements), measure empirical utility per flow per (backend, defense), and report per-flow scores. 
This allows practitioners to understand the effects of the defenses on different user-flows and compute their aggregated utility metric by reweighting the per-flow scores according to the user-flow/user-task distribution for their specific real-world deployment.

We define each flow as a distinct combination of memory usage, inbox access (untrusted read tools), and send functionality (external write tools) that determines which defenses may interfere. 
We experimentally capture utility as the fraction of successful benign task completions in standardized suites (no attack email), one suite per flow. \cref{tab:utility-by-backend-defense} reports these per-flow scores. To obtain a final \emph{aggregated} utility for deployment decisions, we must weight these scores by the distribution of flows in the target deployment. How to obtain and combine these weights is the subject of the second half of this section (\cref{app:obtaining-weights}).

\subsubsection{Seven Representative User Flows}
\label{app:user-task-taxonomy}

We map user-facing workflows to seven security-relevant capability classes. Each corresponds to a distinct (memory, inbox, send) confirguation and sequence.

\paragraph{1. Pure Memory Recall (\texttt{memory\_only}).}
This flow captures situations where the user expects the assistant to remember preferences, facts, or personal context from prior conversations and to have future interactions informed by that stored knowledge. For example, the user may share the name of their manager in one session and expect the agent to correctly fill in the manager's name when workshopping a draft in a later session, without the user having to repeat it.
\textit{Capabilities Required:} Save and recall information from user queries; persistent indexing and cross-session retrieval. No inbox or send tools are used.
\textit{Expected Defense Impact:} Limit-memory-length may truncate stored entries; other defenses have minimal impact.

\paragraph{2. Assistant Output Reuse (\texttt{assistant\_responses}).}
This flow captures situations where the user expects the assistant to recall and reuse its own prior suggestions or outputs. For example, after the assistant recommends a plant for a home garden, the user may ask in a later session ``What did we decide on for my new plant?'' and expect the agent to recall its own recommendation rather than generate a new one.
\textit{Capabilities Required:} Index assistant-generated content into memory; retrieve it across sessions; optional send.
\textit{Expected Defense Impact:} User-prompt-only excludes assistant content from memory, breaking this flow entirely.

\paragraph{3. Inbox Interaction Followed by Recall (\texttt{untrusted\_probe}).}
This flow captures situations where the user interacts with the inbox (e.g., checking unread emails) and then, in the same tainted session, expects the assistant to index the information being shared into memory. This information is probed for in a later session to check if it was indexed into the memory meaningfully. For example, the user may ask ``Remind me what budget I said we had for this event'' and expect recall of prior conversation.
\textit{Capabilities Required:} Inbox read (untrusted tool) followed by memory indexing in the same session.
\textit{Expected Defense Impact:} No-untrusted-tools disables memory indexing after any inbox read, so recall fails.

\paragraph{4. Inbox-Based Reply Without Memory (\texttt{disable\_send}).}
This flow captures situations where the user reads an email and instructs a reply with content fully specified in the query, without relying on recalled memory. For example, the user may say ``Reply: Sounds good, see you at 4pm'' after opening a meeting invitation, with the reply body entirely provided in the instruction.
\textit{Capabilities Required:} Inbox read and send; the reply body is provided by the user.
\textit{Expected Defense Impact:} Provable policy blocks send in sessions marked untrusted (e.g., after inbox read); other defenses allow it.

\paragraph{5. Inbox-Based Reply With Memory (\texttt{untrusted\_send}).}
This flow captures situations where the user expects the assistant to compose and send an email that incorporates information stored in memory from an untrusted session. For example, when opening a pricing inquiry, the user may say ``Reply with my standard consulting rate and availability''---the rate having been stored in a prior session---and expect the agent to recall and include it in the reply.
\textit{Capabilities Required:} Inbox read, memory indexing, and send email that includes information from the untrusted session.
\textit{Expected Defense Impact:} No-untrusted-tools disables memory after inbox read; provable policy blocks send in untrusted sessions. Both can block this flow.

\paragraph{6. Multi-Session Contextual Reply (\texttt{memory\_tools}).}
This flow captures situations where the user expects the assistant to reply to an email by merging inbox content with information from prior trusted sessions. For example, when an email requests study progress, the user may ask ``Reply and include the study hours I told you about'' or ``Reply and add Julia to the thread'' where Julia was introduced in an earlier conversation.
\textit{Capabilities Required:} Cross-session memory, inbox read, and send with merged content from both sources.
\textit{Expected Defense Impact:} Provable policy would block the sending of the email; limit-memory-length may reduce stored detail.

\paragraph{7. Long-Horizon Recall Under Context Pressure (\texttt{long\_memory}).}
This flow captures situations where the user expects the assistant to recall information from the distant past despite extensive intervening context. For example, after many sessions of email use and long conversations (including pasted documents or chat logs), the user may ask ``What time zone did I say my team operates in?'' and expect accurate recall.
\textit{Capabilities Required:} Durable long-term storage and accurate retrieval despite $\sim$1M tokens of intervening context.
\textit{Expected Defense Impact:} Limit-memory-length and context truncation may reduce reliability.

\subsubsection{Obtaining and Combining Utility Scores}
\label{app:obtaining-weights}

We combine per-flow utility scores into weighted utility per (backend, defense):
\[
\mbox{Weighted utility} = \sum_{\text{flow } s} w_s \cdot \frac{\text{Successful benign in } s}{\text{Total benign in } s},
\quad \sum_s w_s = 1.
\]
The choice of weights is crucial. Below we explain our attempt to derive empirically grounded weights from available datasets, why that attempt did not yield a defensible proxy, and why we adopt \emph{deployment profiles} instead.

\subsubsection{Proxy Metric Evaluation}
\label{app:proxy-evaluation}

The seven representative task flows defined in \cref{app:user-task-taxonomy} are not uniformly frequent in realistic deployments. A user who primarily reads and archives email interacts with the agent very differently from one who delegates reply composition or relies heavily on cross-session memory. Reporting only macro-average utility---which assigns equal weight to all seven flows---would misrepresent the real-world impact of defenses on a representative user.

Ideally, weights would be derived from a large-scale log of real users interacting with a memory-equipped AI email assistant. \textbf{No such dataset currently exists.} Commercial systems such as Google Gemini for Workspace and Microsoft Copilot for Outlook do not publish user interaction telemetry at the task-type level~\citep{chi2025email}. We therefore explored constructing a \emph{proxy task-flow distribution} by combining two independent empirical sources, one for each of two orthogonal dimensions that characterise our task flows. We make no claim that such a proxy would accurately describe any specific deployment; rather, we sought a principled alternative to uniform weighting. As we explain below, we could not construct a defensible proxy and \textbf{do not report proxy-derived weights} in this paper.

\paragraph{Task flow decomposition.}
Each of our seven task flows exercises two largely independent dimensions: (1) the \textit{memory demand type}---whether the flow requires no memory, single-session recall of user-provided information, single-session recall of assistant outputs, cross-session reasoning, or long-horizon temporal recall; and (2) the \textit{email action type}---whether the flow involves no inbox access, read-only access, optional send, or read-plus-send.

\paragraph{Source 1: Memory dimension marginal.}
For the marginal over memory demand types, we considered LongMemEval~\citep{wu2024longmemeval}, a benchmark for long-term memory in chat assistants. LongMemEval contains 500 manually curated questions across six types: \texttt{single-session-} \texttt{user}, \texttt{single-session-}{ \texttt{assistant}}, \texttt{single-session-}{ \texttt{preference}}, \texttt{multi-session}, \texttt{knowledge-update}, and \texttt{temporal-reasoning}. These categories were designed to reflect commonly mentioned topics in user-assistant chats. We would map them to our memory vocabulary (e.g., merge single-session-user and single-session-preference into \textbf{Single-session (user)}; map multi-session and knowledge-update to \textbf{Multi-session}). The \textbf{None} memory category (for \texttt{disable\_send}) has no LongMemEval counterpart and would require an arbitrary constant.

\textbf{Limitation:} LongMemEval is a \emph{benchmark} designed by researchers to cover memory abilities---not a log of organic user queries. Its category distribution reflects what the creators wanted to test, not how often users actually perform each type of memory task in an email-agent context. Using it as $P(\text{memory\_dim})$ would conflate ``benchmark coverage'' with ``user workflow prevalence.''

\paragraph{Source 2: Email action dimension marginal.}
For the marginal over email action types, we considered the Avocado Research Email Collection~\citep{avocado2015}. Yang et al.~\citep{yang2017sigir} establish that approximately 38\% of enterprise emails receive a reply. One could set read-only, optional-send, and read-plus-send marginals accordingly, with an upward adjustment to read-plus-send on the grounds that users who adopt an AI email assistant likely delegate high-effort send tasks disproportionately~\citep{chi2025email}.

\textbf{Limitation:} Avocado studies \emph{human-to-human} email behaviour: given an email, does it get a reply? Our flows are \emph{per-session task types} for an AI assistant. The mapping is indirect; Avocado does not provide per-task-type distributions for ``no inbox,'' ``read-only,'' ``optional send,'' or ``read-plus-send'' in an AI-assisted workflow. The ``none'' and ``optional send'' categories have no direct Avocado analogue and would require ad hoc assignment.

\paragraph{Independence assumption.}
The natural approach is to model $P(\text{flow}_i) \propto P(\text{memory\_dim}_i) \times P(\text{email\_action\_dim}_i)$ and normalise. This assumes memory demand type and email action type are uncorrelated.

\textbf{Limitation:} In practice, multi-session memory tasks may be \emph{positively} correlated with send-involving workflows (e.g., ``reply with what we discussed last week''). Assistant-output recall often co-occurs with optional send (e.g., ``send the version you suggested''). The independence assumption is not validated and may systematically misweight several flows.

\paragraph{Deployment specificity.}
Even if a proxy distribution were defensible, it would represent a general-purpose email assistant. Specialised deployments---a customer support agent, a scheduling-only assistant, an executive delegation tool---would have radically different task distributions. Practitioners in such regimes should reweight the per-flow scores in \cref{tab:utility-by-backend-defense} according to their own observed or estimated task mix, which our transparent per-flow reporting makes possible.

\paragraph{Conclusion.}
We could not construct a defensible proxy distribution from available data. The marginals are either absent (no user logs), misaligned (LongMemEval is a benchmark; Avocado is pre-AI human email), or require arbitrary constants. The independence assumption is questionable. We therefore \textbf{do not report proxy-derived weights}. Instead, we adopt deployment profiles as a principled alternative.

\subsubsection{Deployment Profiles}
\label{app:profiles}
We define three deployment profiles over the seven flows (\cref{tab:deployment-profile-weights}), ordered along a spectrum from recall-heavy to email-heavy. \textbf{Recall-focused} emphasizes memory-only, assistant responses, and long-memory; lower weight on send and probe tasks (\cref{fig:utility-profile-recall-focused}). \textbf{Balanced} sits in the middle: moderate weight across memory-only, assistant responses, untrusted probe, memory tools, and long-memory; higher weight on memory-tools and send cases (disable-send, untrusted-send) than Recall-focused (\cref{fig:utility-profile-balanced}). \textbf{Email-heavy} emphasizes disable-send, untrusted probe/send, assistant responses, and memory tools; memory-only negligible (\cref{fig:utility-profile-email-heavy}). Practitioners identify the best-matching profile and interpret the tradeoff accordingly.

For each profile we compute (backend, defense)-specific \emph{weighted utility} (benign task success fraction under that profile's flow distribution) and \emph{security} defined as $\text{security} = 1 - \mathrm{ASR}$ at $N=100$. The figures in \cref{fig:utility-profile-recall-focused,fig:utility-profile-balanced,fig:utility-profile-email-heavy} visualize the security--utility tradeoff for each profile, separately for GPT-5-mini (left) and Gemini 3.1 Pro (right). Points correspond to (backend, defense) configurations.

\textbf{Limitations.} Profiles are plausible scenarios, not data-driven. Practitioners should reweight \cref{tab:utility-by-backend-defense} per their task mix. \textbf{Takeaways.} Across both models, moving from Recall-focused to Email-heavy increases the importance of inbox/send-capable flows, which changes the utility cost of defenses that restrict memory writes after untrusted tools. For the Recall-focused setting (\cref{fig:utility-profile-recall-focused}), the best tradeoff is achieved by \textit{RAG + no untrusted tools}. For both Balanced and Email-heavy settings (\cref{fig:utility-profile-balanced,fig:utility-profile-email-heavy}), \textit{RAG + user\_prompt\_only} is the best combination.

Intuitively, when the deployment is dominated by long-horizon recall rather than email actions, defenses that only block untrusted tool effects preserve more user-facing utility. When email actions carry more weight, restricting what can be stored from untrusted prompts becomes the dominant lever for keeping ASR low without collapsing weighted utility. In all three profiles, RAG tends to concentrate the high-utility region (and therefore frequently participates in the Pareto-optimal points), while more aggressive send-blocking or policy-enforced configurations can shift points toward higher security at a higher utility cost.
